\section{질문과 100개 조건의 정리}
기존 발표의 신규 공격당 100개는 탐색한 10, 20, 50, 100, 200, 400개 중 설명용으로 선택한 조건이다.  통계적 중앙값, 운영 환경에서 관측한 전형적 수량, 최적값 또는 최소 필요량이라는 근거는 없다. 앞으로 100개를 대표 조건으로 정당화하지 않고 전체 예산 곡선을 제시한다. 수량 예시를 사용할 때에는 설명용 예시로 명시한다.

누적 실험도 신규 공격 탐지와 갱신 비용을 측정할 수 있지만, 라벨 공급량과 context 크기가 함께 증가한다. 따라서 제한된 context에서 기존 사례를 보존하며 갱신하는 문제를 분리하지 못한다. 또한 최종 전체 Macro-F1만으로 갱신 전후의 기존 클래스 유지 성능을 판단할 수 없다. 재실험은 \textbf{확보한 라벨 수, 실제 편입 수, 지속 보관하는 context 크기}를 구분하고, 같은 기존 평가 사례에 대한 갱신 전후 예측을 비교한다.

연구 질문은 ``1,000개 context 한도에서 신규 공격의 라벨을 제한적으로 편입할 때, 누적 재학습·누적 context와 비교하여 신규 공격 탐지, 기존 클래스 유지, 갱신 비용이 어떻게 달라지는가''이다. 특정 교체 규칙이 우수하다는 결론을 전제로 하지 않는다.

\section{기존 결과에서 확인한 문제와 아직 확인하지 않은 원인}

\section{고정 조건과 두 데이터셋의 관계}
CIC2018과 ToN-IoT는 \textbf{각각 독립적으로 평가}한다. 서로의 공격 사례를 섞지 않는다. 기존에 정제하고 분리한 각 벤치마크의 train에서 초기 및 신규 사례를 선택하며 test 행은 context·학습·표본 선택에 사용하지 않는다. 초기 1,000개는 기존 실행과 같은 ID를 사용한다. 정상 750개와 기존 공격 두 클래스 각각 125개다. CIC2018의 초기 공격은 Brute force와 DoS, ToN-IoT의 초기 공격은 DoS와 Scanning이다.

공격 도입 순서는 기존 설정을 유지한다. CIC2018은 DDoS, Web attacks, Infiltration, Bot 순이며, ToN-IoT는 DDoS/Injection, Password, XSS, Backdoor/Ransomware, MitM 순이다. 이는 공격 클래스의 순차 도입을 구성한 것으로 전체 raw timestamp의 재생이나 네트워크 환경 이동 평가가 아니다. 신규 공격 라벨은 확보되었다고 가정한다. 라벨을 얻기 전의 미지 공격 탐지와 라벨링 작업 비용은 평가 범위가 아니다.

신규 공격당 확보 라벨 수는 $n\in\{10,20,50,100,200,400\}$다. EXP77/78/80의 중첩된 학습 ID를 유지한다. 모든 방법은 같은 단계에 같은 라벨 후보를 제공받는다. 초기 사례 수, 후보 공급량, 실제 context 사용량을 별도 열로 기록한다. 가중치는 EXP83의 동일 TabPFN v3 checkpoint로 고정하고, 4 estimators, CPU context cache, context subsampling 없음, 동일 query 배치 설정을 유지한다.

\section{핵심 변경: 후보 공급량과 편입량 분리}
지속 context 용량 $B=1{,}000$은 기존 비교와 이어지는 자원 제약이며 최적 크기라는 주장이 아니다. 한 단계에서 새 클래스가 $k_t$개면 후보 공급량은 $k_t n$이다. 신규 후보 전체를 넣는 대신 단계 전체의 편입 상한 $q$를 둔다. 주 비교는 $q=100=0.10B$이고, 보조 비교는 $q=50=0.05B$와 $q=200=0.20B$다. 이 숫자는 후보 라벨 수 100개와 다른 변수다. 5/10/20\%의 갱신 폭을 비교하기 위한 사전 설정이며 test 점수로 고르지 않는다.

기존 클래스별 보호량을 $f_c$라고 할 때 실제 편입량은
\[
 m_t=\min\left(k_t n,\ q,\ B-\sum_{c\in\mathcal{Y}_{t-1}}f_c\right)
\]
로 정한다. 신규 클래스끼리는 가능한 한 균등하게 배분하고, 잔여 수량은 고정 class ID 순으로 배분한다. 각 신규 클래스의 가용 수량을 넘지 않으며 적어도 한 사례가 포함되어야 한다. 불가능한 조건은 실행 전 오류로 검출한다.

예를 들어 ToN-IoT에서 새 공격 두 클래스의 라벨이 각각 400개 확보되면 후보는 800개다. 주 설정에서는 두 클래스에서 각각 50개만 편입하고 기존 context에서 총 100개를 삭제한다. 후보 800개를 확보·검토한 정보 예산과 최종 편입 100개를 모두 기록하며, 이를 ``100개 라벨만 사용한 실험''이라고 부르지 않는다.

\reportfigure{figures/20261020_admission_design.pdf}{교체 비율의 설계값. 기존의 전량 편입과 단계당 100개 상한을 비교한 계산이며 성능 예측이 아니다. ToN-IoT는 한 단계에 두 클래스가 도입될 수 있다.}

\subsection{후보 선택과 메모리 범위}
신규 클래스별로 초기 1,000개에서만 계산한 표준화 변환을 적용한 후, 후보 중심에 가장 가까운 점부터 시작해 이미 선택한 점들과의 최소 거리가 가장 먼 후보를 순서대로 선택한다. 동률은 저장된 train 행 ID로 결정한다. 모든 FIFO/무작위/유사도 삭제 정책은 동일한 편입 ID를 받는다. 선택 계산에는 해당 단계의 신규 후보만 사용하며 미래 클래스나 test는 사용하지 않는다.

이 선택은 큰 후보 집합에서 대표 사례를 고르는 설계 가설이다. 무작위 편입 대조도 별도로 둔다. 단순히 중첩 집합의 앞 100개를 고정 선택하면 100/200/400 조건에서 context가 같아져 후보 수 비교가 무의미할 수 있으므로 이를 피한다. 동일 context가 생성된 조건은 ID hash로 확인하고 중복 추론을 재사용하되 결과 행과 선택 비용은 각각 보존한다.

편입되지 않은 후보와 삭제된 과거 사례는 다음 단계에서 다시 가져오지 않는다. 전체 라벨 후보를 읽고 선택하는 임시 작업 메모리는 1,000개 context 제한에 포함되지 않는다. 따라서 $B=1{,}000$을 전체 시스템의 저장량 또는 GPU 메모리 상한으로 표현하지 않고, 일시 후보 수·실제 메모리 사용량을 함께 기록한다.

\section{기존 클래스 보존과 삭제 규칙}
정상은 최소 500개, 이미 알려진 공격은 클래스당 최소 25개를 보호한다. 해당 클래스가 지금까지 실제 편입한 총 사례가 더 적으면 그 수를 보호한다. 이는 정상·공격 정보의 소실을 막기 위한 비교용 제약이며 충분한 탐지 품질을 보장하거나 최적 비율을 뜻하지 않는다. 주 조건은 보존량을 고정하고, 보조 조건에서 기존처럼 클래스당 1개만 남기는 경우와 비교한다.

\begin{description}[leftmargin=1.7cm,style=nextline]
\item[FIFO] 확보 단계가 오래된 사례부터 삭제한다. 같은 단계 안의 순서는 class/file 정렬에 좌우되지 않도록 seed 43의 저장된 무작위 동률 순서를 사용한다. 오래되었다는 사실을 실제로 쓸모없어졌다는 뜻으로 해석하지 않는다.
\item[무작위] 현재 기존 context에 대해 단계별 고정 seed의 삭제 순서를 생성한다.
\item[유사도] 초기 표준화 공간에서 편입할 신규 사례까지의 최소 유클리드 거리가 작은 기존 사례부터 삭제한다. 서로 다른 클래스의 가까운 사례가 경계 구분에 중요할 수 있으므로, 삭제된 클래스·거리와 오탐 변화를 함께 기록한다.
\end{description}
세 정책 모두 삭제할 때마다 보호량을 점검한다. 보호량을 위반하는 사례는 건너뛰고 정확히 $m_t$개를 삭제한 뒤 신규 $m_t$개를 추가한다. 보존 규칙과 편입 ID를 같게 두어 기존 사례 중 무엇을 삭제하는지 비교한다.

주 비교는 데이터셋 2개, 후보 수 6개, PFN 버퍼 정책 3개로 36조건이다. 누적 PFN과 누적 XGB가 각각 12조건이며, 같은 버퍼 XGB 대조 12조건을 합하면 72조건이다. 기존 최종 예측을 참조할 수는 있지만, 같은 실험 환경의 새 갱신 시간과 이전 실행 시간을 혼합해 속도 우위를 주장하지 않는다. 새로운 단계별 유지 평가를 위해서는 중간 모델 상태가 필요하다.

보조 비교는 후보 수 400개와 무작위 삭제를 사전에 고정해 수행한다. (1) $q=50$, (2) $q=200$, (3) $q=100$에서 클래스당 1개만 보호, (4) $q=100$에서 대표 선택 대신 무작위 신규 편입을 비교한다. 주 조건과 비교하여 교체 폭, 보호 규칙, 신규 선택의 영향을 나누어 본다. 두 데이터셋에서 총 8개 PFN 조건이다. 결과가 좋아 보이는 정책을 test로 고른 뒤 보조 비교를 붙이지 않는다. 연구 목적상 필요하면 이후 별도 설계로 확장한다.

\section{기존 성능 유지와 신규 탐지의 평가}
모든 주 결과는 \textbf{마지막 상태의 모델로 같은 전체 test를 평가}한다. 단계별 예측을 합쳐 최종 점수처럼 제시하지 않는다. 전체 Macro-F1, 정상 오탐률, 클래스별 precision/recall/F1, 초기 공격군과 이후 도입 공격군을 구분해 보고한다. 새 공격의 F1은 해당 공격의 양성 사례만 평가해서 계산하지 않고 다른 클래스에서 발생한 false positive도 포함한다.

갱신 전후 분석에는 클래스당 최대 2,000개의 고정 평가 패널을 기존 test에서 seed 43으로 한 번 추출한다. 이는 저장된 단계별 모델의 오프라인 사후 진단이며 실시간 시간순 재생이 아니다. 모든 단계에서 같은 행 목록과 라벨과 독립적으로 섞은 같은 query 배치를 사용한다. 패널에는 미래 클래스의 \emph{query 특징}이 있을 수 있지만, 정답은 평가에만 사용하고 context·표본 선택·전처리에는 전달하지 않는다. 미지 클래스 탐지 성능으로 해석하지 않는다. 현재까지 알려진 클래스 행에 대한 혼동행렬을 별도로 계산한다. 이 고정 query 구성은 PFN의 query 배치 구성이 바뀌는 효과를 통제하기 위한 것이다.

갱신 단계 $t$ 직전에 알려진 클래스 집합을 $\mathcal{Y}_{t-1}$이라 하자. 같은 집합에 속한 \emph{동일 패널 행}에서 갱신 전 모델과 갱신 후 모델의 점수를 비교한다. 예를 들어 기존 클래스 Macro-F1의 변화는
\[
 \Delta F^{\mathrm{old}}_t=F(f_t;Q_{\mathrm{old},t})-F(f_{t-1};Q_{\mathrm{old},t})
\]
로 정의한다. 점수 계산 시 기존 클래스 목록을 명시하고 신규 클래스로 잘못 예측한 행도 오류로 계산한다. 초기 세 클래스의 고정 패널 점수도 단계마다 별도로 추적한다.

기존 행만으로 계산한 F1에는 신규 클래스에서 기존 클래스로 들어오는 오탐이 반영되지 않는다. 따라서 현재까지 도입한 전체 클래스 행에서 얻은 기존 클래스 precision/F1, 신규 클래스 recall/F1, 정상 FPR을 함께 제시한다. 새 클래스의 개선과 기존 클래스의 손상을 한 개의 전체 Macro-F1로 상쇄해 설명하지 않는다.

seed는 43 한 번이다. 기존에 살펴본 holdout을 사용하는 탐색적 실험임을 밝힌다. 같은 성능이라는 통계적 동등성이나 ``최소 $n$개면 충분''이라는 보장은 하지 않는다. 허용 가능한 기존 성능 손실과 신규 탐지 목표가 별도로 정해지지 않은 상태에서는 품질·라벨 수·비용 곡선을 제시한다.

\section{갱신 비용과 해석 범위}
주 비용은 초기 단계 이후의 후보 선택, 기존 삭제, 모델 구성, 전처리, fit/context cache 준비 시간의 합이다. GPU 동기화 후 측정하고 같은 장치에서 순차 실행한다. 초기 준비, 추론, checkpoint 저장, 검증, 보고서 생성은 주 갱신 비용에서 제외하되 원시 기록에 별도로 보존한다. 동일 버퍼 XGB도 편입·삭제 선택 비용을 포함한 전체 갱신 시간과 순수 fit 시간을 각각 기록한다. 다른 방법과 선택 계산을 공유했다면 공유 여부를 명시하고 배포 시 필요한 선택 비용을 누락하지 않는다.

작은 수량만 교체하더라도 현재 구현은 1,000개 context 전체의 전처리·표현·캐시를 다시 준비할 수 있다. \textbf{교체 상한은 사례 구성의 변화를 제한하고, 버퍼 상한은 context 처리 크기를 제한}한다. 둘을 incremental cache 갱신이나 무료 업데이트로 설명하지 않는다. 전체 추론 시간도 기록하되 발표의 갱신 시간과 구분한다. 순간 메모리, 단계별 편입·삭제 수, 실제 교체 비율, 클래스별 보유 수를 저장한다.

Ma 등, \emph{In-Context Data Distillation with TabPFN}은 TabPFN 가중치를 고정하고 context의 특징값에 경사를 전달하여 작은 입력 집합을 최적화한다. 원 실험은 1,000개의 클래스 균형 context와 고정 라벨을 사용하며, Adam 학습률 0.01 및 validation AUC 기반 선택을 적용한다. 실제 사례를 삭제·보관하는 FIFO 등의 정책과 달리 context 입력값이 학습된다. \subsection{소규모 pilot의 구체적 설계}
먼저 두 데이터셋에서 신규 공격당 10개와 400개라는 양 끝 조건만 사용한다. seed 43, 총 4개 최적화 실행으로 하고, 단계마다 context를 새로 초기화한다. 현재까지 공개한 \textbf{누적 원시 학습 사례를 다시 참조}하여 최적화하므로 엄격한 과거 원시 데이터 보관 제한을 만족하는 실험으로 분류하지 않는다. 고정되는 것은 추론에 제공할 context token 1,000개의 수다.

각 클래스의 실제 사례를 초기화용과 query용으로 분리하고 최소 절반은 query로 남긴다. 현재 클래스에 가능한 한 균등하게 1,000개 token을 할당하며, 실제 초기화 사례가 부족하면 같은 seed 사례를 반복하여 token을 초기화한다. 실제 unique 라벨 수와 중복 token 수를 별도 기록한다. 이 반복은 새 라벨 확보가 아니며 최적화 전 대조도 정확히 같은 token과 라벨을 사용한다. 기존 EXP75의 초기화 함수를 그대로 사용하면 작은 라벨 예산에서는 1,000개보다 적은 context가 만들어질 수 있으므로, 반복 초기화 규칙과 실제 token 수를 명시적으로 구현·검증한다.

모든 token의 특징만 Adam 학습률 0.01로 최적화하며 라벨과 backbone은 고정한다. 실제 query는 현재까지 공개한 모든 클래스의 query 후보에서 경험적 분포에 따라 batch 256으로 복원 추출한다. 0, 20, 100 step을 사전에 정한 예산으로 모두 보고하고 test로 가장 좋은 step을 선택하지 않는다. 원 논문의 validation 기반 early stopping과는 다른 고정 계산 예산 실험이며 추가 validation 라벨을 사용하지 않는다.

원시 특징의 외부 표준화는 초기 1,000개에서만 정하고 고정한다. EXP75에서 확인한 differentiable 경로의 유한 gradient 보완을 적용하고 수치 parity를 다시 점검한다. 단일 differentiable estimator를 사용하는 최적화 상태와 step 0 대조의 전처리·초기화·라벨·모델 설정을 모두 같게 둔다. 주 실험의 4-estimator 실제 사례 버퍼와 비교할 때는 estimator 수, 라벨 배분, 전처리, 누적 데이터 접근, 중복 token이 다르므로 최적화 한 요소의 효과로 해석하지 않는다.

갱신 비용에는 token 초기화, context 역전파, optimizer, 최종 추론용 준비를 모두 포함한다. 초기 단계 비용과 후속 갱신 합계, optimizer 포함 최대 메모리를 기록한다. 학습된 특징 token은 실제 생성 가능한 네트워크 flow를 뜻하지 않는다. 여기에서만 모델 입력 context를 합성·최적화하는 것이며, 원본 IDS 평가 데이터가 합성되거나 두 벤치마크가 결합되는 것은 아니다.

이 pilot이 유용하면 다음 설계에서는 과거 원시 사례 재접근을 금지한 조건에서 실제 replay/anchor와 학습 token을 하나의 총 저장 예산에 포함해야 한다. 신규 사례만으로 context를 최적화하고 과거 정보도 자동 보존된다고 가정하지 않는다. 이번 계획은 먼저 삭제 기반 버퍼의 개선과 별도로 ICD의 압축 품질·최적화 비용을 확인하도록 구분한다.
