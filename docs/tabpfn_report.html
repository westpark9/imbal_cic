TabPFN 메모리 부족 원인과 대안 실험

2026-08-18 · TabPFN 8.2.0 · tabpfn-v3-classifier-v3_20260417_multiclass.ckpt · RTX 4090 실측

모든 실험 결과 표는 test 샘플 수 내림차순으로 정렬돼 있습니다.

결론. TabPFN은 체크포인트의 MAX_NUMBER_OF_SAMPLES = 1,000,000에 막혀 100만 샘플보다 더 넣기 어렵습니다. 이전에 full data를 참여시킨 것은 disjoint bagging(estimator마다 겹치지 않는 부분집합을 주고 확률 평균)을 시도한 것이며, 이 방식은 TabPFN 원 논문에 없습니다.

1메모리 부족 원인

TabPFN에서 fit()은 학습이 아니라 학습셋을 프롬프트로 받아두는 것입니다. 그래서 predict()를 부를 때마다 학습셋 전체가 GPU로 다시 올라갑니다.

시간  = n_estimators × test 배치 수 (forward 횟수)
메모리 = 학습 컨텍스트 전체 + test 배치 하나

estimator와 배치는 순차 실행이라 메모리는 곱해지지 않고 시간만 곱해집니다.

실측 (RTX 4090, 46 feature)값
fit() 후 GPU 상주0.198 GiB (모델 가중치뿐, 데이터 0)
학습 행당18,530 B
test 행당12,343 B
100만 행 컨텍스트약 17.5 GiB

왜 100만이 상한인가

  • 체크포인트가 MAX_NUMBER_OF_SAMPLES = 1,000,000을 선언하고 초과 시 에러를 냅니다.
  • 가드를 꺼도 메모리가 선형으로 늘어 막습니다 — CIC2018 전체 1,207만 행 = 213 GiB(A100 80GB의 2.8배).
  • 멀티 GPU는 estimator를 나눌 뿐 하나의 컨텍스트를 쪼개지 않습니다.

해결 (결과 불변).

  • PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True + test를 한 배치로 → 조각화 제거, 6.85시간 → 26.7분
  • fit_mode="fit_with_cache" + keep_cache_on_device=False → 학습 컨텍스트 K/V를 한 번만 계산, peak 21.1 → 16.6 GiB

full data를 넣으려면 disjoint bagging밖에 없습니다. SUBSAMPLE_SAMPLES=k를 주면 estimator마다 겹치지 않는 k행을 가져가므로 n_estimators = ⌈전체/k⌉면 풀을 100% 덮습니다. 다만 각 예측기는 여전히 k행에만 조건화되고 앙상블은 확률 평균이라 "전체로 학습"이 아니라 "분할 학습 후 평균"이며, TabPFN 원 논문에 없는 방식입니다.

2실험 결과

공통 설정: 클래스별 chronological 60/20/20, val 미사용, seed 42, XGBoost 300 trees / depth 8 / lr 0.05, class weighting 없음, test cap 없음(test pool 전체 평가).

test cap을 뺀 것이 숫자를 바꿉니다. 이전 회차는 test_cap_per_class=100000으로 평가했는데, 이는 test 쪽 클래스 분포를 인위적으로 평탄화해 소수 클래스 precision을 부풀립니다. 학습 조건이 완전히 같고 test cap만 다른 두 CIC2018 full-XGB 런을 비교하면:

test 행 수로 줄을 세우면 붕괴가 tail 전용 현상이 아님이 보입니다. BoT-IoT에서 F1 0.031인 ddos는 test 143만 행으로 그 데이터셋의 2위 규모이고, ToN-IoT에서 F1 0.001인 scanning은 27만 행으로 5위입니다. 반대로 test 8행뿐인 CIC2017 infiltration은 0.857로 멀쩡합니다. 샘플 수와 F1은 이 표에서 거의 무관합니다.

+몇몇 클래스가 0.0을 기록한 원인

학습 데이터가 부족해서가 아닙니다. 클래스별 chronological split이 train과 test에 서로 다른 시기의 트래픽을 넣기 때문입니다. 같은 클래스라도 시간이 지나면 다른 것이 됩니다.

진단은 이진 프로브 AUC로 합니다 — 같은 클래스의 train 행과 test 행을 구분하도록 분류기를 학습시켜 AUC를 잽니다. 0.5면 같은 개체군, 1.0이면 완전히 다른 개체군입니다.

train (0–1172)   변화 후 데이터    0 행   ← 모델이 보는 것
val   (1173–1563) 변화 후 데이터   98 행   ← 사용 안 함
test  (1564–1955) 변화 후 데이터  392 행   ← 평가 대상

즉 모델은 한 번도 본 적 없는 행동을 알아보라는 요구를 받습니다. 실제로 val을 학습에 넣으면 F1 0.000 → 0.810으로 회복됩니다.

다만 val을 넣는 것이 일반 해법은 아닙니다. 같은 조작이 CIC2018의 web_attacks는 0.603 → 0.090으로 악화시켰습니다. 위상 변화가 val 구간에 걸린 경우에만 통합니다. 그리고 ToN-IoT / scanning은 val을 넣어도 0.001 → 0.005로 회복되지 않습니다 — 80%를 학습해도 test 시기의 트래픽이 학습셋 어디에도 없는 경우입니다.

단, 이 절의 숫자는 test cap 100k 체제에서 얻은 것입니다 (web_attacks 0.603이 cap 있는 baseline 값). cap 없는 baseline은 0.162이므로 val 투입 효과는 cap 없는 조건에서 재확인이 필요합니다.
