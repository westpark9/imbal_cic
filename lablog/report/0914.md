# 2026-09-14 — EXP42: dedup 벤치마크 위의 방법 비교 (클래스별)

## 1. 무엇을 왜

0911의 EXP41은 "동일 벡터·상반 라벨을 데이터셋 전체에서 지우면 성능이 오르는가"를 두 모델(full-train XGBoost, TabPFN composed-C0)로만 봤다. 사용자 요청으로 같은 네 벤치마크 위에서 (a) 처리가 **클래스별로** train·test를 몇 행으로 바꾸는지, (b) 그 위에서 xgb · tabpfn · ours · SOTA가 **클래스별로** 어떻게 갈리는지를 본다. 보고서에서 EXP40(train만 처리, test는 원본)은 제거했다 — 가설의 조건이 아니었고, 손실 위치 진단은 EXP41·EXP42의 bucket 분해가 대신한다.

## 2. 스크립트

`tabpfn/scripts/nfv3_v3_exp42_dedup_methods.py` (새 frozen 실험). dedup + 재split 블록은 `nfv3_v3_exp41_dedup_dataset_tabpfn.py`에서 그대로 복사했으므로 arm별 train/val/test 행이 EXP41과 동일하다(첫 smoke에서 확인: dedup_xy의 `xgboost_full` macro 0.7613 = EXP41 XGB 기록값, `test_idx` 완전 일치).

| 방법 | 학습·컨텍스트 | 비고 |
|---|---|---|
| `realistic_oracle` | — | 완벽 라우팅 + 충돌 벡터는 다수 라벨 = 그 test의 천장 |
| `xgboost_full` | 처리된 train 풀 전체 | EXP41 run의 예측 재사용, `test_idx` 일치 검증 후 |
| `xgboost_c0` | C0 100k | 정보 예산 짝지음 |
| `tabpfn_plain` | 무작위 100k (비율 보존) | 소박한 컨텍스트 기준선 |
| `ours_c0` | 구성된 C0 100k (exp31) | benign 0.75 · 공격 균등 · n_estimators 4 |
| `distpfn` | ours 확률 + prior 보정 | exp37과 같은 5줄 보정, 같은 forward pass 재사용 |
| `boostpfn` | C0 풀에서 T=50 × 500행 | exp35와 같은 설정 |
| `localpfn_knn` | 행마다 C0에서 1,000행 국소 검색 | exp36과 같은 설정, `--batch-size-inf` 128 → 256 |

두 SOTA는 각자 vendored TabPFN-v1을 갖고 top-level 모듈 이름(`utils`/`scripts`/`methods`)이 겹치므로 한 프로세스에서 같이 import하면 안 된다 — 스크립트가 그 조합을 거부하고, 캠페인은 phase를 나눠 돈다.

### 비교의 한계 (보고서에도 명시)

- `tabpfn_plain`은 train 풀 **전체**에서 100k를 뽑고, C0를 쓰는 방법들은 pool의 context 파티션(50%, scenario 층화)에서 뽑는다. 크기는 같고 풀이 다르다 — 기준선에 불리하지 않은 방향이다.
- EXP42는 seed 42 한 번이다. arm 간 차이는 EXP41의 3-seed 폭(원본 0.0023 → 충돌 벡터 삭제 0.0286)과 비교해서 읽어야 한다.
- 열마다 test가 다르므로 가로 비교는 "그 벤치마크에서의 점수"다. 같은 열 안의 세로 비교만 방법 간 비교다.

## 3. 운영 기록

- 13:27 smoke 3종. `xgb_full` 재사용·`boostpfn` 통과. `localpfn_knn`은 `--batch-size-inf 1024`에서 CUDA OOM(5.87 GiB 추가 할당 실패, 프로세스 18.9 GiB 점유) → 256으로 내림(7.7 GiB, ~1.6 it/s → 1.76M행 기준 arm당 ~1.2 h).

- 13:31 캠페인 시작(`scratchpad/exp42/campaign.sh`): phase 1 = TabPFN 계열 4 arm 병렬, phase 2 = BoostPFN 4 arm 병렬, phase 3 = LoCalPFN 2 lane.
- 14:52 phase 3을 **순차 1 프로세스**로 교체했다. GPU 병렬은 총 시간을 줄이지 못한다(측정): 단독 1.28 it/s(327행/s), 2 lane 1.65 s/it씩(합 310행/s), batch 512 단독 1.55 s/it(330행/s). 단독 실행에서 이미 `utilization.gpu` 100%라 lane을 늘리면 처리량이 나뉠 뿐이다. 15:36에 다른 GPU 작업을 붙였을 때도 LoCalPFN이 1.28 → 0.89 it/s로 31% 떨어졌다. **단일 GPU에서 ETA를 줄이는 방법은 없고, 남은 arm을 다른 장비로 나누는 것이 유일한 수단이다.**
- `pkill -f <패턴>`이 내 셸까지 두 번 죽였다(exit 144). 패턴 문자열이 그 명령 자신의 커맨드라인에 들어 있으면 `[n]` 브래킷 트릭도 소용없다. 대상 PID를 먼저 찾아 `kill <pid>`로 끝내는 게 안전하다.

### 4b. 방법 × 처리 (macro-F1, seed 42)

| 방법 | 원본 | 중복 제거 | 충돌은 다수 라벨 | 충돌 벡터 삭제 |
|---|---:|---:|---:|---:|
| 현실적 oracle (천장) | 0.8564 | 0.9974 | 1.0000 | 1.0000 |

| TabPFN-v3 (무작위 100k) | 0.7282 | 0.7411 | 0.7321 | 0.7541 |
| **ours (구성된 C0 100k)** | **0.7616** | **0.8055** | **0.7977** | **0.8039** |

| LoCalPFN TabPFN-kNN | 0.7121 | 0.7690 | 0.7588 | 0.7402 |

판정 세 가지.

1. **ours가 4/4 최고다.** 무작위 100k 컨텍스트 대비 +0.033 / +0.064 / +0.066 / +0.050이고, 차이는 전부 꼬리에서 온다(중복 제거 arm: infiltration 0.078 → 0.249, web 0.142 → 0.469). 중복을 지운 벤치마크에서도 컨텍스트 구성의 기여가 살아 있다 — 오히려 원본(+0.033)보다 크다.
2. **full-train XGBoost도 넘는다.** 중복 제거 arm에서 0.7613 → 0.8055. 같은 C0를 준 XGBoost(0.8043)와는 사실상 동률이라, 이 벤치마크에서 이득의 대부분은 *모델*이 아니라 *컨텍스트 구성*에서 온다. 원본 arm에서만 ours가 XGB-c0를 0.009 앞선다. **정정(0915)**: 원시값으로 다시 보면 충돌 벡터 삭제 arm에서도 ours가 XGB-c0를 +0.012 앞선다(0.8039 vs 0.7919). 동률권은 중복 제거(+0.0011)·충돌은 다수 라벨(+0.0021) 두 arm이다. 다만 EXP41 3-seed로 보면 dedup 세 arm 모두 seed 43·44에서 XGB-c0가 ours를 앞서므로(0915.md §2) seed 42 단일 run의 ours 우위는 원본 arm에서만 seed 폭 밖이다.
3. **SOTA는 처리할수록 더 나빠진다.** BoostPFN 0.7368 → 0.6636, DistPFN 0.6681 → 0.6041. 둘 다 "꼬리를 과대표집한 컨텍스트"를 전제하지 않은 보정·재가중이라, C0가 일부러 만든 구성을 되돌리는 방향으로 작동한다.

재현 확인: 원본 arm이 09-08 기록과 일치한다 — XGB-c0 0.7525(기록 0.7525), ours 0.7616(0.7617), BoostPFN 0.7368(0.7369), LoCalPFN-kNN 0.7121(0.7121). 네 방법이 모두 재현되므로 dedup arm의 수치도 같은 파이프라인 위의 값으로 볼 수 있다.

LoCalPFN은 dedup 세 arm에서 ours보다 0.037–0.064 낮다. 주목할 점은 infiltration으로, 0.122–0.155로 SOTA 중 가장 낮다. 국소 검색이 모순 지역에서 이웃을 고르면 그 이웃들이 서로 다른 라벨을 갖기 때문으로 보인다. 모순이 많은 클래스에서 retrieval 계열이 특히 불리하다는 증거다. **정정(0915)**: 원시 per_class_metrics로 다시 보면 infiltration이 SOTA 중 가장 낮은 것은 LoCalPFN이 아니라 BoostPFN(0.071 / 0.062 / 0.040)이고 DistPFN도 중복 제거·다수 라벨 arm에서 LoCalPFN보다 낮다(0.121 / 0.135). "retrieval 계열이 특히 불리하다"는 해석은 근거가 없어 철회한다.

주의: EXP42의 `ours_c0`는 EXP41의 seed 42 값과 0.001–0.006 차이가 난다(예: 충돌 벡터 삭제 0.8039 vs 0.7975). C0 추첨은 동일하고, 같은 프로세스에서 `tabpfn_plain` fit·predict가 먼저 돌아 TabPFN 내부 config 추첨의 전역 RNG 상태가 달라진 것이 원인으로 보인다. 0904에서 문서화한 "단일 config 복권"(0.675↔0.750)의 축소판이며, arm 간 차이를 읽을 때 이 폭을 함께 고려해야 한다.

## 4c. 남은 칸 — 중복 유지 + 모순 제거 (EXP44, 09-15 00:09 완료)

2×2로 놓으면 지금까지의 arm은 세 칸만 채운다. dedup_majority가 모순을 다수 라벨로 해소하긴 하지만 중복도 함께 지워 train이 12,069,313 → 5,283,411행이 된다. 두 손잡이가 엉켜 있다.

|  | 모순 유지 | 모순 제거 |
|---|---|---|
| **중복 유지** | 원본 (train 12,069,313) | **EXP44** |
| **중복 제거** | dedup_xy (5,295,822) | dedup_majority (5,283,411) / drop_conflict (5,271,045) |

`tabpfn/scripts/nfv3_v3_exp44_conflict_only.py`. `--conflict-only relabel_majority`는 모순 벡터의 모든 행을 다수 라벨로 바꾸고 **행을 지우지 않는다** — test 행이 원본 arm과 동일하므로 같은 행 위에서 비교된다. `drop_vectors`는 모순 벡터를 통째로 지우되 나머지 중복은 유지한다. LoCalPFN은 arm당 3.4시간이라 제외했다. XGBoost full-train은 기록 run이 없어 스크립트 안에서 새로 적합한다.

주의: 다수 라벨을 train+test 전체에서 계산하므로 Arp et al.(USENIX Sec'22)의 selective snooping에 해당한다. 벤치마크 구성용 진단 arm이지 배포 가능한 전처리가 아니다.

|---|---:|---:|---:|
| 현실적 oracle | 0.8564 | 1.0000 | 1.0000 |
| XGBoost (train 전체) | 0.7548 | **0.8467** | 0.7968 |
| XGBoost (C0 100k) | 0.7525 | 0.7774 | 0.7921 |
| TabPFN-v3 (무작위 100k) | 0.7282 | 0.8055 | 0.7590 |
| ours (구성된 C0) | 0.7616 | 0.8140 | 0.7923 |
| DistPFN | 0.6681 | 0.8106 | 0.7931 |

train 행: 원본 12,069,313 / 재라벨 12,069,313(삭제 0, 재라벨 210,728행) / 벡터 삭제 8,853,245.

**판정 두 가지.**

1. **모순을 없애면 순위가 뒤집힌다.** 재라벨 arm에서 full-train XGBoost가 0.8467로 ours(0.8140)를 앞선다. 원본에서는 ours가 앞섰다. 모순이 사라지면 12M행을 통째로 외우는 쪽이 유리해지고 컨텍스트 구성의 이점이 줄어든다. 벡터 삭제 arm에서는 셋이 0.792–0.797로 사실상 동률이다. **ours의 우위는 모순이 있을 때만 나타난다** — 우리 주장에 불리하지만 이것이 데이터가 말하는 바다.
2. **행을 지키더라도 꼬리는 흡수된다.** 재라벨은 행을 하나도 지우지 않는데도 test 기준 web 509 → 163행(32.0%), infiltration 37,631 → 20,086행(53.4%)이 되고 dos의 slowhttptest가 brute_force로 넘어가 brute가 118.3%로 늘어난다. 벡터 삭제 arm은 더 심해서 infiltration 24.9%, brute_force 32.8%, web 30.6%만 남는다. Raskovalov 외에서 mitm이 1,052 → 0이 된 것과 같은 현상이다. 그래서 두 arm 모두 macro 상승분의 상당 부분이 "모델이 좋아져서"가 아니라 "어려운 행이 사라지거나 쉬운 클래스로 옮겨가서"다.

결론: 모순은 지워도, 고쳐도 꼬리를 잃는다. §1c의 3분해와 클래스별 천장을 원본 벤치마크 위에서 병기하는 쪽이 여전히 맞다.



## 5. ours v2 (설계만, 보류)

`tabpfn/scripts/nfv3_v3_exp43_ours_majfill.py`를 썼고 **사용자 판단으로 실행은 보류**했다(2026-09-14). 기록만 남긴다.

동기: 표의 ours는 구성된 C0를 받은 frozen TabPFN-v3이고 그 이상이 아니다. scorer·verifier 층은 EXP38·39에서 6조건 모두 global을 선택했다(Δglobal = 0). 그래서 "ours를 발전시킨다"는 라우팅이 아니라 컨텍스트 구성에서 찾아야 한다.

THE KNOB `--attack-fill`: 예산·클래스 균형·benign 행을 모두 고정한 채 **공격 클래스 할당량을 어떤 행으로 채울지**만 바꾼다. `majority_consistent`는 그 벡터의 데이터셋 전체 다수 라벨이 해당 클래스인 행을 우선 쓴다(현실적 oracle이 그 벡터에 주는 답과 같다). `clean`은 다른 라벨이 전혀 없는 벡터만 우선한다. 근거는 0911 감사다 — infiltration 행의 75.1%, web의 69.6%가 상반 라벨 트윈이라 균일 추첨은 infiltration 슬롯의 3/4을 benign과 구분 불가능한 벡터에 쓴다. dedup_xy에서 infiltration 풀 14,059행 중 다수 라벨 일치 행이 7,139개이고 할당량은 5,965라 전량을 학습 가능한 행으로 채울 수 있다.

검토 후 버린 대안: 고유 벡터 비례 배분(ddos가 고유 벡터의 65%를 차지해 infiltration 몫이 4,847 → 1,488로 감소), 컨텍스트 배깅(exp32 0.751–0.758 < 단일 추첨 0.7638), 풀 dedup·사본 상한(exp31·exp33 음성), 라우팅 계열 전부(EXP38·39 + SRC_HISTORY 6종).

한계: dedup_majority·drop_conflict arm은 충돌이 이미 제거돼 이 knob이 무효다. 실제로 갈리는 벤치마크는 원본과 중복 제거 둘뿐이다.

### 대조군 검증에서 나온 것 (이건 실행함)

`--attack-fill natural`로 dedup_xy를 돌려(`tabpfn/results/20260914_154808_..._exp43_ours_natural_dedup_xy_s42`) 신규 스크립트가 exp42의 ours와 같은 행을 뽑는지 확인했다. 클래스별 목표 수가 완전히 일치하고(benign 75,000 / bot 841 / brute 5,967 / ddos 5,966 / dos 5,966 / inf 5,965 / web 295) 추첨 seed(42+990)와 추첨 함수가 같으므로 **컨텍스트 행은 동일**하다. 그런데 macro-F1은 0.8055(exp42) vs 0.8087(exp43)로 0.0032 어긋난다. ddos 0.945 → 0.957, web 0.469 → 0.484.

원인은 TabPFN config 추첨의 전역 RNG 상태다(exp42는 같은 프로세스에서 `tabpfn_plain`이 먼저 돌았다). **함의: 컨텍스트 knob을 비교할 때는 반드시 같은 스크립트·같은 프로세스 순서의 natural 대조군과 비교해야 한다.** exp42 값과 비교하면 ±0.003의 가짜 개선을 볼 수 있다. 0904의 "단일 config 복권"(0.675↔0.750)이 n_estimators=4에서도 완전히 사라지지 않았다는 증거이기도 하다.
