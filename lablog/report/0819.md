## 1. 두 XGB는 같은 문제를 푸는 분류기가 아니다

| | track A (`s43`/`s44`) | track B (`tabpfn/nfv3_v3_common.py`) |
|---|---|---|
| benign | label space에서 삭제 (`s44:1237-1239`) | 보통 class |
| unseen class | train·test 양쪽에서 제거 | 없음 (`--unseen` 자체가 없음) |
| sample weight | `sqrt(N/(K·n_c))` (`s44:577`) | 없음 (`nfv3_v3_common.py:637`) |
| train cap | 2M **비층화** random (`s44:1301`) | 1M 또는 uncapped |

hyperparameter·feature·split code는 byte-identical (300 trees / depth 8 / lr 0.05 / sub 0.8 / col 0.8 / seed 42, 46 feat, 같은 pkl).

### 결정적 사례

**ton_iot `scanning`**: track A `xgb_f1 = 0.9992` vs track B `0.0009`. 같은 class, 같은 split.
차이는 benign이 label space에 있느냐 하나뿐이다. `scanning` 행의 **97.13%**가 benign 행과
byte-identical이므로(`probe_m1_exact_collision.csv`) benign이 있으면 전부 benign으로 간다.
benign을 지우면 나머지 attack과는 자명하게 갈린다.

benign 항은 13개 config 전부에서 부호가 바뀌지 않는 유일한 항이고 median **+0.1012**.
dataset별로는 cic2018 +0.1014, ton_iot +0.1499, **bot_iot 정확히 0.0000**.
bot_iot의 gap은 전부 unseen 제거 항이다 — `--unseen dos`에서 잔차 +0.3325 중 `ddos`
(0.0311→0.9932)가 96.5%. dos:ddos = 1.12:1이므로 imbalance가 아니라 **label collision**.

### s44 baseline은 스스로 0.20을 버리고 있다

`xgb_ladder.csv`, bot_iot `--unseen ddos`, 고정 test set, 한 번에 knob 하나:

| rung | rows | classes | sqrt w | macro | theft F1 | theft recall |
|---|---|---|---|---|---|---|
| S0 track B (5-class) | 10,160,284 | 5 | ✗ | 0.5731 | 0.388 | |
| S1 −benign | 10,129,091 | 4 | ✗ | 0.5115 | 0.389 | |
| S2 −unseen | 5,838,562 | 3 | ✗ | 0.7840 | 0.389 | 0.2415 |
| S3 +sqrt weight | 5,838,562 | 3 | ✓ | **0.9830** | **0.986** | 0.9907 |
| S4 +2M cap = **기록된 baseline** | 2,000,000 | 3 | ✓ | 0.7836 | 0.389 | 0.2415 |

S4가 기록된 `0.7838483289638832`(`results/20260804_121642_.../4a`)를 소수 3자리까지 재현한다.

**즉 `--max_global_train 2000000`이 0.1994를 깎고, sqrt weight가 직전에 0.1990을 벌어준다.
기록된 0.78385는 두 knob가 우연히 상쇄된 지점이고 논문은 둘 중 어느 것도 논하지 않는다.**
`subset_indices`(`exp_utils.py:141-147`)는 pooled index 위 균일 random draw라 stratification이 0이다.
theft train 969행 → ~332행이 되고 sqrt weight로도 복구가 안 된다.
같은 파일에 `cap_by_family`(`s44:389`)가 있고 val/test/target-OOD에는 쓰이는데 global XGB train pool에만 안 쓰인다.

→ bot_iot/ddos의 진짜 XGBoost bar는 **0.983**이고, expert pipeline(0.637)의 격차는
−0.147이 아니라 **−0.346**이다.

### 판정

**둘 다 그대로는 baseline으로 부적절하다.**
- track B: `--unseen` 개념이 없어 open-set 프로토콜과 무관
- track A: 같은 run/split/seed는 맞지만 attack-only closed-set이고, unseen·benign leg에
  XGB 숫자가 **존재한 적이 없다** (`s44:2597-2604`는 `known_attack` scope, `6a/6b`에 XGB 대응물 없음)
- 그리고 track A의 숫자는 `--unseen` 하나로 **0.2989 ~ 0.9714**를 오간다. 수식어 없이
  "the XGBoost baseline"이라 부를 수 없다.

## 2. "ton_iot tail을 잘한다"는 test cap artifact다

같은 fitted model, `test_cap_per_class`만 다른 one-knob 쌍
(`20260817_163506` vs `20260818_113117`) — per-class recall이 16자리까지 동일:

| class | support | recall (동일) | F1 @cap100k | F1 @cap없음 |
|---|---|---|---|---|
| mitm | 1,204 | 0.7309 | 0.746 | **0.162** |
| ransomware | 795 | 0.9409 | 0.819 | **0.150** |
| backdoor | 40,678 | 0.9984 | 0.999 | 0.998 |
| **tail_avg** | | | **0.782** | **0.156** |

per-row FPR은 0.16%뿐인데 그게 mitm support의 7.3배, ransomware의 10.6배다.
**tail은 recall 문제가 아니라 precision 문제이고, cap이 FP pool을 줄여 없앤 것뿐이다.**

가설을 실제로 지지하는 class는 `backdoor` 하나(purity 0.9992, F1 0.998 uncapped)인데
203,384행으로 tail이 아니다(`dos` 203,456과 동급). tail이라 부르는 건 `s44:112-117`뿐이다.

그리고 그 숫자는 pipeline이 아니라 baseline XGB의 것이다 — expert F1은 `mitm` 12/12 run에서
0.0000, `ransomware` 11/12에서 0.0000. `tail_macro_f1_expert = 0.3328` = (0.9985+0+0)/3 =
**backdoor 혼자**.

## 3. overlap이 known leg를 설명한다 (단서 있음)

`overlap_probe.py`. byte-identical feature row가 다른 label을 갖는 비율:
cic2018 **26.7%**, bot_iot **6.1%**, ton_iot **60.7%**.

22개 class에서 `corr(1-NN label purity, XGB per-class F1) = +0.901`,
`corr(log support, F1) = +0.035`. **support는 설명력이 없다.**
XGBoost는 1-NN ceiling에서 median 0.108 이내 — 이미 이 표현의 Bayes floor 근처다
(bot_iot theft: XGB recall 0.2415 vs purity 0.2446, headroom +0.003).

⚠ **단서**: test 행이 train 행과 byte-identical인 비율이 ton_iot scanning 0.974,
cse2018 bot 0.955, ton_iot ddos 0.964다. test의 85~97%가 train에 그대로 있는 곳에서
1-NN purity는 manifold 기하가 아니라 **동일 레코드 간 label 충돌**을 재고 있고, 높은 F1은
memorization일 수 있다. 기하 해석이 온전한 건 bot_iot `ddos`(중복률 5.6e-06) 하나.

### dataset 결함 (cic2018)

(`IN_BYTES=60, OUT_BYTES=40, IN/OUT_PKTS=1, TCP_FLAGS=22, FLOW_DURATION=1`).

`5c`의 `dos,flood,brute_force,21110`(dos test의 34.84%, `resolvable_by_argmin_rate=0.0000`)이 이것이다.

## 4. unseen leg 실패의 실제 원인 — gate가 아니라 결정 규칙

### 4.1 `unseen_resolved_acc`는 "모든 expert가 거부"와 항등이다

26개 run에서 `unseen_resolved_acc`와 `6b`의 `unseen/all_out` share의 최대 절대차 = **0.0**.
`resolve_predictions`(`s44:1099-1141`)에서 `"unseen"`을 낼 수 있는 줄은 `in_counts == 0`
하나뿐이다(2,617줄 전체에서 유일).

### 4.2 gate 자체는 멀쩡하다

`3b` 84개 (expert, run) 쌍: unseen role AUROC **median 0.9721**, 자기 tau에서 detect 0.8709.
non_owned_known_attack AUROC 0.9967. **ranking은 이미 좋고 무너지는 곳은 threshold와 집계다.**

### 4.3 benign expert가 절반을 먹는다

attack expert만의 만장일치 reject: median **0.3107** / mean 0.3547 (`5b`).
benign expert 합류 후 최종: median **0.1375** / mean 0.1751. → 비용 mean **0.1796**.

최악: `20260803_112753_..._unseen_bot_noextaux` — 0.98515 → **4.81e-05**.
benign expert `unseen_false_in_rate = 0.99995`, unseen 41,542행 중 **41,460행이 benign**(`6a`).

benign expert 27개 run 집계: ID(benign) 유지 0.905, **known** attack 오수용 0.109,
**unseen** attack 오수용 **0.417**(max 1.000). 3.8배 차이 — 판별 경계는 negative가 있던
방향만 막는다는 교과서적 실패.

역방향도 이미 깨져 있다: benign 행의 **71.7%**가 `argmin` branch로 흘러 accuracy 0.215.

### 4.4 pooled quantile이 tail을 죽인다

`4b_all.csv` 152개 class×config, expert 내 support rank별 **gate가 삼킨 recall**:

| rank | n | median | mean |
|---|---|---|---|
| 1 (head) | 84 | 0.011 | 0.056 |
| 2 | 49 | 0.103 | 0.381 |
| **3** | 19 | **0.995** | 0.870 |

`xgb_recall>0.8` & `gated_recall<0.1`인 쌍 **24/152**, 전부 `ransomware`(12)·`mitm`(8)·
`web_attacks`(4)이고 전부 rank 2~3. 이 셋의 1-NN purity는 0.956/0.864/0.906 —
**overlap 문제가 아니다.** `threshold = np.quantile(val["energy"], 0.95)`(`s44:1529-1531`)가
pooled quantile이라 expert의 head class가 정하는 순수 calibration artifact.

### 4.5 multi-class owner expert는 자기 semantic family 안의 novelty를 볼 수 없다

`external_aux_for_expert`(`s44:442-450`)가 `excluded_semantics`를 `configured_owned`
(= JSON 전체 ownership, **held-out class 포함**)에서 만든다.
`1b_expert_aux_composition.csv`, bot_iot `--unseen ddos`:

```
flood | configured_owned=ddos,dos | excluded_semantics=ddos,dos
  cse_cic_ids2018/ddos → EXCLUDED: owned semantic  (available 1,324,350, selected 0)
  cse_cic_ids2018/dos  → EXCLUDED: owned semantic  (available   302,966, selected 0)
```

unseen ddos를 거부해야 하는 유일한 expert가 네 데이터셋 어디에서도 flood류 negative를
0행 받는다. 그 expert의 unseen AUROC = **0.5036**(우연).

`active_owned`로 바꾸면 external ddos가 들어오지만 그건 held-out family를 외부 경유로
보여주는 leakage다. → **버그가 아니라 프로토콜의 대가**이고, semantic family 단위 expert
grouping 설계의 구조적 한계다. `owner_expert_fully_removed=False` 19개 median 0.109 vs
완전 제거 9개 median 0.157.

**그리고 tail을 버려서 사는 게 아니다.** val-calibrated q95, per-class tau 기준:
known 유지 sample **0.953** / **macro 0.921** / worst class 0.774, benign 유지 0.781,
unseen→benign 누수 median **0.013**.
비교: s44의 attack-expert-only 규칙은 macro known 유지 **0.746**, worst class는
theft 0.81 / mitm 0.98 / ransomware 0.96 / web_attacks 0.99가 거부된다.

### 주의 3개

1. **MSP는 benign이 label space에 들어오면 무너진다** (median 0.080). 세션 초반에 잡았던
   "global XGB + MSP가 pipeline을 이긴다"는 attack-only label space에서의 결과이고
   benign을 넣으면 전이되지 않는다. 값을 하는 건 **distance**다.
   bot_iot ddos의 MSP AUROC는 **0.278**로 chance 미만 — unseen이 known보다 더 확신을 받는다.
2. **bot_iot 3개 config는 distance 규칙이 완패한다.** 거기서는 s44가 낫다.
   ddos:dos = 1.12:1 near-duplicate이고 uncapped pool이 7.15M/8.03M이라 reference set이
   공간을 촘촘히 덮어 거리가 안 갈린다. capped suite로 재면 0.61/0.69가 나오는데 그건 regime artifact다.
3. **ton_iot `scanning`은 진짜 irreducible.** 세 방향 독립 확증 —
   (a) benign과 97.13% exact collision, (b) raw-kNN open-set AUROC 0.357(chance 미만),
   (c) benign 포함 모델에서 unseen→benign 0.972.

### 기존 "irreducible bucket" 분류는 기각

M3 ceiling 기반 8/28 bucketing은 성립하지 않는다. bot_iot의 `median_id_dist_to_kept`가
0.015~0.182(다른 dataset은 0.000~0.003)라 threshold가 엉뚱하게 잡혔고, bucket 8개 중
**6개에서 실제 성능이 ceiling을 초과**한다(bot_iot dos 0.3106 vs ceiling 0.0006).
살아남는 건 ton_iot scanning 2개 config뿐.

그리고 unseen leg에는 연속 예측변수가 없다(28행 회귀: leak 질량 R²=0.045 p=0.36,
M3 tpr R²=0.0008 p=0.90, owner_fully_removed R²=0.071 p=0.17). 같은 기하 안에서의 분산이
기하 사이의 분산보다 크다 — `bot_iot/reconnaissance`가 aux knob 하나로 0.1375 → 0.6393.
**따라서 0.1246은 데이터의 성질이 아니라 calibration의 성질이다.**

## 6. cascade(stage 0 hard filter)는 재제안 금지

`SRC_HISTORY.md:376-396`, `s25_code_ood_v2.py`가 정확히 그 구조다. 최종 run 로그:

> "Baseline known macro-F1: 0.8695 / MoE known macro-F1: 0.1298 / Friday OOD detect rate: 0.0000"

exp0 energy prefilter가 세 평가 set 전부에서 행의 100%를 통과시켜 open-set 다리가 no-op이 됐다.
삭제된 `code_cascade.py`(`:136`)도 같은 계열.

stage-1 후보를 직접 재봐도(cse2018/bot, benign-val 누수 5% 고정):

| gate | known 통과 | unseen 통과 |
|---|---|---|
| discriminative XGB | 0.857 | **0.016** |
| support kNN10 | 0.732 | 0.992 |
| Mahalanobis | 0.117 | 0.000 |
| IsolationForest | 0.112 | 0.000 |

판별형은 unseen의 98.4%를 benign으로 흘리고(= 지금 benign expert와 같은 메커니즘),
density형은 known attack의 27~89%를 되돌릴 수 없이 삭제한다.

→ **benign은 label space의 class로 넣고 reject region을 하나만 남긴다.** 행을 데이터 흐름에서
제거하지 않으므로 되돌릴 수 있고, benign이 positive codeword를 가지면 all-reject의 preimage가
unseen 하나로 유일해진다.

## 8. 다음 run (한 run = knob 1개, seed 42, 첫 줄 `Args:` 전량 덤프)

**연구자의 원 질문에 문자 그대로 답하는 run**: expert bank가 규칙과 별개로 기여하는가.
지면 그게 결론이고 논문은 architecture 논문에서 measurement 논문으로 간다.

E0(cap 수정)과 E1(benign as class)을 묶지 말 것 — 같은 다리를 반대 방향으로 민다
(+0.20 bot_iot vs −0.10~−0.14 ton_iot).
