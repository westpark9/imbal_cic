## 1차 확인: 인덱싱 버그인가

- `scripts/preprocess_cic2017_full_raw.py`: `y = LabelEncoder().fit_transform(...)`,
  `class_names = label_encoder.classes_.tolist()` — `class_names[i]`가 `y==i`와 항상 일치하도록
  sklearn이 보장. 버그 아님.
- `exp_utils.labels_for`: `{name: i for i, name in enumerate(class_names)}` 매핑을 cic2018
  로더 전체에서 동일하게 재사용 — 별도 인코딩 경로 없음. 버그 아님.
- `exp_utils.scenario_chronological_split`: 클래스(scenario)별로 **개별** 60/20/20 분할
  (`for scenario in sorted(np.unique(scenarios[indices]))`) — docstring이 말하는 "per-class"
  그대로 구현되어 있고, 전역 quantile로 자르는 버그 없음.

→ 세 지점 모두 코드상 결함 없음. 실제 원인은 데이터/split 특성.

## 2차 확인: `bot`/`infiltration` = real train/test distribution shift

`train_used` count 확인 결과 두 클래스 모두 학습 샘플이 아주 적은 건 아니었음
(`bot`=691, `infiltration`=12 — `heartbleed`는 겨우 4개로도 f1=1.0을 찍는 것과 대비됨). 즉
"학습 샘플 부족"만으로는 설명 안 됨.

`time_proxy`를 까보면 `bot`은 파일 하나(`6_Friday-WorkingHours-Morning.pcap_ISCX.csv`, 원본
CIC-IDS2017의 Bot 캡처 세션) 안의 in-file row order, `infiltration`도 마찬가지로 하나의 파일
(`5_Thursday-WorkingHours-Afternoon-Infilteration.pcap_ISCX.csv`) 안에 몰려 있음. per-class
chronological split은 사실상 "같은 세션 안에서 앞쪽 60% vs 뒤쪽 20%"로 자르는 것과 동일.

직접 측정 (`Xtr = X[train_idx of class]`, `Xte = X[test_idx of class]`, `z = |mean_tr-mean_te|/std_tr`,
70 feature 전체의 median):

| class | train_n | test_n | median &#124;z&#124; | 최대 z 특징 |
|---|---|---|---|---|
| `bot` | 1,173 | 392 | **0.28** | `Fwd IAT Min` z=7226.8 (train mean 27.6 → test mean 504,000) |
| `infiltration` | 21 | 8 | **0.59** | `Fwd IAT Min` z=8.0 (train mean 2.07e5 → test mean 7.06e6) |
| `ddos` (control) | 76,815 | 25,605 | 0.08 | — (표면적 큰 z는 std≈0인 degenerate 컬럼 artifact) |
| `portscan` (control) | 95,282 | 31,762 | 0.04 | — (동일 artifact) |

`bot`/`infiltration`은 median |z|가 control 대비 3.5~15배 높고, IAT(inter-arrival time)
계열 feature가 세션 초반부와 후반부에 수백~수천 배 다름 — Bot의 C2 비콘 주기나 Infiltration의
다단계(침투→lateral movement→exfiltration) 공격이 캡처 세션 내에서 시간에 따라 행동 패턴이
바뀌는 것으로 보임. **TabPFN·XGBoost 둘 다 독립적으로 정확히 0을 찍은 이유**가 바로 이거:
두 모델 다 train에서 본 적 없는 분포의 test를 받은 것 — 알고리즘 문제가 아니라 "짧고 단일
세션인 다단계 공격을 클래스별 chronological split으로 자르면 구조적으로 OOD test가 된다"는
split 방법론 자체의 특성.

## 3차 확인: cic2018 `web_attacks` (xgboost만 0) = starvation

이 run은 `--max-train-samples 100000`. sota 정책은 자연 클래스 비율을 유지한 채
stratified subsample하므로, `web_attacks`의 자연 train pool(1,522)이 전체 pool
(11,069,303, benign이 10,508,775로 압도) 대비 차지하는 비중만큼만 배정됨:

```
1522 * 100000 / 11069303 ≈ 13.75 → floor 13
```

`split_audit.csv`의 `train_used` 행이 실제로 `web_attacks: 13`을 확인. XGBoost의 multiclass
softmax는 13개짜리 클래스로는 10^5~10^7개짜리 클래스들과 경쟁에서 전혀 못 이김
(→ recall 0). TabPFN은 in-context few-shot 설계 덕에 같은 13개로도 f1=0.560을 냄 — 알고리즘
간 샘플 효율성 차이. 이것도 버그가 아니라 "작은 `--max-train-samples`에서 sota의 비율보존
정책이 tail class를 굶긴다"는 알려진 트레이드오프(스크립트 자체 docstring에도 명시).

## Takeaway

- 두 run 모두 **인덱싱/코드 버그 없음**. 원인은 (a) 클래스별 chronological split이 짧은
  단일세션·다단계 공격에 대해 구조적으로 train/test를 다른 분포로 쪼개는 문제, (b) 작은
  `--max-train-samples`에서 sota의 비율보존 정책이 극소수 클래스를 거의 0개로 굶기는 문제 —
  둘 다 방법론적으로 이미 예견 가능했던 특성이지 회귀는 아님.
- (a)는 재현 가능한 진단 함수(`diagnose_train_test_drift`, median train/test feature z-score
  per class)로 노트북에 박아넣었음 — 다음에 이상하게 0 나오는 클래스가 있으면 이 셀로 바로
  구분 가능(진짜 drift vs 단순 starvation).
- (b)는 지금 Colab에서 더 큰 GPU를 쓸 수 있게 됐으니(아래) `--max-train-samples`를 올려서
  재확인해볼 가치 있음 — 다만 `bot`/`infiltration`류는 budget을 올려도 (a) 문제라 해결 안 됨.

## Colab 노트북 작성 (`tabpfn/nfv3_cic2018_multiclass_test_colab.ipynb`)

로컬 4090에서 못 돌리는 스케일(cic2018 전체 등)을 Colab의 더 큰 GPU로 시도할 수 있도록
작성. 로컬 `nfv3_cic2018_multiclass_test.py`와의 차이:

1. Drive 마운트 — 데이터 pkl을 Drive에서 읽고, `per_class_metrics.csv`/`split_audit.csv`/
   `args.json`/`timings.json`을 Drive의 `results/`에 저장. **학습된 모델도 재사용 가능하게
   저장**: XGBoost는 `booster.save_model()`, TabPFN은 `tabpfn.model_loading.
   save_fitted_tabpfn_model()`(foundation weight는 빼고 fitted state만 저장, 작음) +
   `load_fitted_tabpfn_model()`로 재적합 없이 즉시 predict 가능 — 로컬에서 실제 저장→재로드→
   predict까지 end-to-end로 검증함.
2. `--protocol reproduce`(랜덤 split + class당 3,000 고정 cap) 완전 삭제.
   `random_stratified_split`, `per_class_train_cap` 분기 전부 제거 — 이제 chronological split
   + `--max-train-samples` stratified budget(구 sota)만 존재.
3. 위 drift 진단(`diagnose_train_test_drift`)을 매 run 전에 자동 실행하도록 박아넣음.
4. `--target-dataset`에 `bot_iot`/`ton_iot` 추가 (사용자 요청). `nfv3_energy_suite_*.pkl`이
   원래 `cse_cic_ids2018` 외에 `bot_iot`(16.9M rows, 5 class)/`ton_iot`(27.5M rows, 10
   class)/`unsw_nb15`(2.4M rows, 미연결)를 같은 스키마로 묶어놓고 있었다는 걸 확인하고,
   `load_cic2018`을 `load_nfv3_suite_subset(args, dataset_name)`으로 일반화해서 재사용.
   `nfv3_energy_suite_cic2018_scenarios.pkl`(이름과 달리 4개 데이터셋 전부의 capped
   슬라이스를 담고 있음: bot_iot=353,604 / cse_cic_ids2018=602,538 / ton_iot=809,984 /
   unsw_nb15=227,693)를 `*_capped` 타겟들의 기본 데이터로 지정 — 전부 60/20/20 split에
   필요한 최소 클래스당 row 수를 만족함(최소가 bot_iot의 `theft` 1,615개).
5. GPU 메모리 기반 `max_train_samples` 자동 제안 셀 — [0812 대화](없음, 이번 세션 채팅
   로그 참고)에서 실측한 RTX 4090 스케일링(`mem_GB ≈ 0.23 + rows/57,900`, 1.5M행부터
   OOM 시작, plateau 없음)을 그대로 사용. cic2018/bot_iot/ton_iot의 uncapped 전체는
   어떤 단일 GPU로도(Colab A100 포함) 안 들어가니 `_capped` 타겟이나 낮춘
   `max_train_samples`를 쓰라고 명시.
