왜 XGBoost를 못 넘는가

답이 나왔습니다. 격차 0.055의 절반은 두 모델에게 준 데이터량 차이였고, 나머지는 ddos·infiltration 두 클래스에 몰려 있었습니다. 분할 방법과 채택 단위를 바꾼 결과 시스템은 0.6978 → 0.72~0.74(3반복), 남은 격차는 −0.015~−0.035입니다. 부산물로 global의 재현성 대역이 25배 줄었고, expert bank 가설은 기각됐습니다.

기준선 — 학습 데이터량별 XGBoost, 그리고 우리의 위치

XGBoost를 두 조건으로 재측정했습니다: 전체 12.07M행(공식 기준선)과, global이 컨텍스트로 받는 것과 동일한 1M행(정보예산을 맞춘 보조 기준선).

이 섹션이 다루는 단계: C0 컨텍스트 — 무엇을 보여줄 것인가

기존 분할은 클래스 단위로 시간순 정렬 후 앞 50%를 컨텍스트(C0) 풀로 떼었습니다. 그런데 brute_force 클래스는 ftp 공격(앞) + ssh 공격(뒤)이 시간순으로 붙어 있어, 50% 컷이 ftp 안에서 끝나 C0에 ssh가 0행이 됐습니다. 같은 이유로 dos의 hulk, web_attacks의 sql_injection도 0행.

부산물 — global 재현성 25배 재현성 대역 = 같은 설정·같은 seed로 같은 run을 반복했을 때 global macro-F1이 흔들리는 폭. GPU bf16 연산은 실행마다 비트 수준으로 조금씩 달라 확률값이 미세하게 변하는데, C0에 없던 scenario 행들은 global이 크게 틀리는(경계가 얇은) 행이라 이 미세 변동이 예측을 수만 행 단위로 뒤집었습니다(한 반복에서 infiltration 0.39→0.21). 그 행들이 C0에 포함되자 뒤집힘이 사라져 대역이 0.027 → 0.0011.

03

지금 시스템의 구조 — 병목이 어디인가

분할 변경 이후의 시스템을 한 장으로. 수치는 층화 분할 3반복 중 최고 run(exp29 r3, delta +0.018) 기준입니다.

expert 형성 자체는 문제 없나 "틀렸다"기보다 가치를 더하지 못하고, 불안정의 진원입니다. ① 내용은 유효 — 이 뱅크로 oracle 0.84가 나옵니다. ② 그러나 형성 방식(residual 서명 KMeans)이 등메모리 무작위 선택보다 낫지 않고(Gate 1 기각), ③ KMeans가 1.93M짜리 잡탕 1개 + 112~405행짜리 미세 regime들로 갈라지는 구조라 run마다 K가 2↔5로 요동 — 재현 불안정과 게이트 셧다운(4/7)의 진원입니다. ④ 미세 regime expert는 블록이 컨텍스트의 1% 미만(공유 anchor 12,761행이 지배)이라 반쯤 퇴화 상태. 결론: expert를 더 정교하게 만드는 방향이 아니라 더 단순하게(K 축소·최소 크기 규칙) 만들고 게이트를 고치는 방향이 데이터가 가리키는 길입니다.

이 섹션이 다루는 단계: verifier — 채택 문턱의 단위

개입 흐름: scorer가 후보를 제안 → expert 실행 → verifier가 이득을 예측 → 예측값이 문턱을 넘으면 답 교체. 이득과 채택 조건의 정의:

G = wc × ΔNLL   (wc = N / (7·nc),  N = 12,069,313)
채택:  q̂ > 21.145   (전 클래스 공통 문턱)
자격(상한):  완벽한 expert여도 Gmax = wc·NLLglobal 이므로  NLLglobal > 21.145 / wc  ⇔  pglobal(정답) < e−21.145/wc

wc는 클래스가 희귀할수록 커서(아래 표), 같은 문턱 21.145가 클래스마다 전혀 다른 난이도가 됩니다:

변경: verifier의 학습 목표를 G → G / wc = ΔNLL로 — 채택 조건이 「ΔNLL > τ」(전 클래스 공통, nat 단위)가 되어 위 표의 wc 열이 비교에서 소거됩니다. scorer는 그대로입니다.

잡음의 사슬: 원천 = TabPFN 추론(bf16, global·expert) → 증폭 = 뱅크(KMeans의 K 요동 2↔5) → 발현 = 문턱 보정(연속 잡음을 가능/불가능 이진 판정으로 바꿔 셧다운)

시스템 delta = 시스템 − global (개입층이 얹는 개선폭). bf16/fp32는 GPU 수치 정밀도 포맷으로, bf16 연산은 실행 순서가 비결정적이라 같은 입력에도 매번 미세하게 다른 확률이 나옵니다. fp32+결정성 커널은 PyTorch가 문서화한 완전 결정성 조합이라 동일 명령 2회가 완전히 같은 결과를 내는지(A/B 해시 비교)를 시험 중입니다.

최고 성능 run — 조건과 클래스별 지표

조건: exp29(층화 분할 + verifier 단위 ΔNLL + 등메모리 대조) · K=5(자동 선택) · τ_pre 0.8835, τ_post 0.25 · prior T 1.25 · seed 42 · bf16 비결정 · 동일 설정 3반복 중 r3. 같은 run 안에서 XGB·oracle 동시 계산.
