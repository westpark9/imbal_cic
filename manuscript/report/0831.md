### 0.2 SSH 라벨 예산 곡선 — **50행이면 회복되고 포화한다** [완료]

`scripts/race_budget_diag.py --budgets c0,c0+ssh50,...`. C0(1M) + D_expert에서 뽑은
ssh_bruteforce N행으로 XGB 재학습, 동일 eval:

| budget | train rows | macro | tail | brute F1 | **ssh recall** | ddos F1 |
|---|---|---|---|---|---|---|
| c0 | 1,000,000 | 0.7283 | 0.5341 | 0.7246 | **0.0** | 0.99973 |
| **c0+ssh50** | 1,000,050 | **0.7565** | **0.5343** | **0.9157** | **0.9984** | 0.99974 |
| c0+ssh200 | 1,000,200 | 0.7559 | 0.5332 | 0.9154 | 0.9968 | 0.99974 |
| c0+ssh1000 | 1,001,000 | 0.7541 | 0.5289 | 0.9159 | 0.9995 | 0.99955 |
| c0+ssh5000 | 1,005,000 | 0.7535 | 0.5292 | 0.9159 | 0.9950 | 0.99500 |

**읽는 법**
1. **50행이면 끝난다.** brute F1 0.7246 → 0.9157(+0.191), macro +0.028. 가이드 §17의
   라벨 예산 격자 B ∈ {0,50,200,1000} 중 **가장 작은 값**이다.
2. **그 이상은 이득이 없고 미세하게 나빠진다**(macro 0.7565 → 0.7535, tail 0.5343 → 0.5292,
   ddos 0.99974 → 0.99500). 여기서는 행을 *추가*만 했는데도 그렇다. §17은 **고정 메모리**를
   요구하므로 실제 refresh는 자리를 비워야 하고, 그러면 손해가 더 커진다.
   → refresh 설계는 "많이 넣기"가 아니라 **"정확히 무엇을 50행 넣을 것인가"** 문제다.
3. **c0+ssh50의 macro 0.7565는 full XGB 바 0.7548을 넘는다** — 1,000,050행이 12,069,313행을
   이긴다.

**축 B에 대한 함의 (좋은 소식이자 나쁜 소식)**
- 좋은 소식: 지금 split 그대로도 refresh가 **원리적으로 작동한다**. B=50에서 한 클래스가
  통째로 회복된다. TabPFN은 in-context라 XGB보다 sample-efficient하므로(0813: 13행으로
  f1 0.560, XGB는 0) 이 50행은 **느슨한 상한**이다.
- 나쁜 소식: 이 실험이 곧 arm(iv)("B행을 C0에 붙이기만 한 global, experts·scorer·verifier
  없음")의 대리이고, **그게 이미 이긴다.** 따라서 exp31의 사전 등록 예측은
  "**일을 하는 것은 context 패치이지 RACE 기계가 아니다**"여야 하며, RACE가 주장할 수 있는
  것은 정확도 우위가 아니라 (a) 재학습 없이 context 편집만으로 같은 회복을 한다는 **비용**,
  (b) 고정 메모리에서 무엇을 넣고 뺄지 고르는 **선택 규칙**뿐이다. 이 둘 중 하나도
  arm(iv)를 못 이기면 축 B를 버린다(§2.3).
- 주의: 이건 XGB 대리 실험이다. TabPFN의 in-context 거동은 다를 수 있고, 그 확인이 exp31이다.

## 1. 클래스별 성능이 안 좋은 원인

**격차의 위치부터.** exp23 run, per-class F1:

| | XGB | RACE | Δ |
|---|---|---|---|
| brute_force | 0.9159 | 0.7246 | **−0.191** |
| ddos | 0.9921 | 0.8951 | **−0.097** |
| dos | 0.7822 | 0.6978 | −0.084 |
| benign / bot / inf / web | | | −0.013 / +0.001 / −0.009 / +0.010 |
| macro | 0.7548 | 0.7001 | −0.055 |
| **tail_avg**(bot·inf·web) | 0.5331 | **0.5337** | **+0.001** |

선언한 tail에서는 이미 동률이다. 격차는 brute·ddos 두 클래스에서 온다. (넘어야 할 최강 XGB는
1M anchored-context의 **0.7605**.)

### 원인 A — brute: C0에 SSH가 0행 (우리 split의 결함, drift 아님)

`brute_force` = ftp(train 232,032) + ssh(train 113,084)이고 SSH는 전부 FTP보다 뒤인데,
context/expert/route 하위 분할이 **클래스 내부 시간순**이다:

| 하위 split | brute 배정 | 구성 |
|---|---|---|
| D_global(C0·anchor) | 172,558 | **전부 FTP** |
| D_expert | 86,279 | FTP 59,474 + SSH 26,805 |
| D_route | 86,279 | 전부 SSH |
| D_tune | 46,015 | **전부 FTP** |

→ (i) C0에 SSH가 없어 global이 test SSH 37,696행 전량 오답(recall 0.6723 = 정확히 FTP 비율),
(ii) D_tune에 SSH가 없어 SSH regime(coverage 0.5212, 후보 중 최고)이 min-support로 삭제.
**`oracle_random_bank`는 brute recall 0.9998** — D_expert에서 무작위로 뽑은 블록이면 SSH가
들어가므로 그냥 고쳐진다. residual bank만 못 고친다. 즉 method 문제가 아니라 버그이고,
고쳐서 macro가 +0.027 올라도 **residual specialization의 성과로 제시하면 안 된다.**

### 원인 B — ddos·benign: 채택 문턱이 사실상 클래스 필터

채택 조건 `q̂ > q_corr = 21.145`의 단위가 **w_bal 가중 CE**다. γ=1이라 w_c = N/(7·n_c)이므로
expert가 완벽해도 `w_c · NLL_global > 21.145`인 행만 자격이 있다:

| class | w_bal | p(정답)이 이하여야 | 오답 중 자격 |
|---|---|---|---|
| infiltration | 15.27 | 0.250 | **98.98%** (25,219/25,480) |
| dos | 9.49 | 0.108 | 34.9% (13,646/39,098) |
| brute | 5.00 | 0.0145 | 100% (expert 없음) |
| **ddos** | 2.17 | 5.9e-05 | **0%** (0/45,886) |
| **benign** | 0.164 | 1e-56 | **0%** (0/14,496) |

ddos는 45,886행이 틀렸고 `dense_oracle`이 F1 0.905 → **0.998**로 고칠 수 있는데(= macro
+0.0133) 손실 단위 이득이 문턱의 1/10이라 **완벽한 verifier로도 한 행도 못 넣는다.**
**target/metric 불일치**: 파이프라인은 w_bal 가중 CE를 최적화하고 논문은 macro-F1을 보고한다.

### 원인 C — infiltration: verifier가 이득을 예측하지 못함

자격 행이 오답의 99%(25,219행)이고 제안도 18,142행 받았는데 **채택 0**이다.

- `4b`: verifier 예측 ↔ 실제 gain 상관 **0.05~0.15**(하나는 −0.073). 사실상 무상관.
- 출력이 expert-상수가 아니라 **class-상수**: e4·e5의 클래스 간 g_lower 확산 **0.00**.
  infiltration의 g_lower **최댓값 −14.63** → τ_post ≥ 0인 어떤 문턱으로도 통과 불가.
- `4c`: τ_pre를 ρ=0.35 → 1.0으로 완전히 열어도 채택 **+191행(+1.7%)**.
  → **병목은 제안 관문이 아니라 post-call verifier다**(status 문서의 진단은 수정 필요).

원인은 exp24b가 scorer에서 이미 고친 병과 같다 — verifier는 여전히 6자릿수 스케일의 raw gain
위에서 quantile 회귀를 한다. **grouping으로는 못 고친다**(e5 내부에서 benign과 inf가 같은 값).

### 원인 D — dos는 이미 천장

자격 행 13,646개 중 12,405개 채택 = **허용치의 91%**. 더 짜낼 것이 없다.

### 원인 E — 판정 자체의 신뢰도 문제 (셋)

1. **잡음 0.027**: knob과 무관한 global macro가 8 run에서 0.6461~0.6734(전 run `prior_T=1.25`,
   `beta=0`으로 동일하므로 prior 탓 아님 → 추론 비결정성). 최근 판정 크기(exp23c +0.003,
   exp23d −0.005, 24b↔24b-off +0.015)가 **전부 이 대역 안**이다. 균일하지도 않다 —
   exp24a에선 global infiltration이 0.393 → **0.205**로 반토막.
   행 집합이 sha256까지 같아도 residual이 **99.93% 행에서 다르고**, 그 결과 작은 regime 구성이
   바뀐다(`[…,8707, 523, 140]` vs `[…,3852, 130, 9]`).
2. **Gate 1 판정 불가**: residual 블록 합 228,638 vs random·proximity 5×186,000 = 930,000
   (**4.07배**). `exp24b:1560-1600`에서 대조군만 항상 186,000을 쓴다. run마다 왜곡 크기가 달라
   순위가 뒤집힌다(exp22c는 residual 우위, 24b-off는 proximity 0.9217 > 0.8294로 열위).
3. **oracle 상한이 부풀려져 있다**: eval 4.02M 중 distinct 2.10M(중복 48%). brute FP가
   **21,110행 = `dos_slowhttptest` test 행 수와 정확히 일치**하고 oracle을 뺀 모든 모델에서
   동일하다(알려진 라벨 충돌). 그런데 `dense_oracle`만 brute precision 1.0인데, 이는
   label-informed oracle이 **정답을 보고 expert를 배정해 충돌을 "해결"**하기 때문 —
   배포에선 불가능하다.

  expert**다(diversity_select가 1.98M행에서 186,000행을 새로 뽑는다). §1.5의 "단일 expert가
  oracle의 91.5% 회수"는 **run이 아니라 `route_gain.npz` 오프라인 재분석**으로 답할 질문이다.
  섞어 인용하지 말 것. (부수 효과: K=1이면 대조 bank가 자동으로 등메모리가 된다.)
- `--lambda-cost`는 살아 있지만 **dense oracle과 대조 bank의 손실에도 λ·c가 더해진다.**
  λ 스윕에서 `dense_oracle`·`oracle_*_bank`·`oracle_utility_recovery`는 λ에 따라 움직이므로
  **비교에서 빼거나** `route_gain.npz`로 λ=0에서 재계산해야 한다. 스윕은 제안 *비율*이 아니라
  **제안 *구성*** 스윕으로 보고한다.

**exp26 설계 주의(검증에서 정정)**: `b_OOF`는 sign(G)가 아니라 *적합된* 분위수 모델의 부호이고
w_bal[y]는 feature에 없으므로, OOF 적합까지 정규화하면 b_OOF가 이동한다. b_OOF는 scorer 타깃에
들어가므로(λ=0에서 사실상 유일한 입력) 제안 관문이 함께 움직여 "문턱이 클래스 필터이길
그만뒀다"와 "scorer가 다른 행을 제안한다"를 구분할 수 없게 된다. → **OOF 적합은 raw로 고정**해
knob을 post-call verifier에 가뒀다. 가이드 §15에 충실한 판본은 별도 run exp26b.

**exp28에서 드러난 것**: `diversity_select`는 regime 크기 ≤ 블록 예산이면 `arange(n)`을 그대로
반환한다. 기준 run에서 regime 5개 중 **4개가 그 경우**(15,468 / 20,718 / 6,322 / 130 ≤ 186,000)
이므로 **§11.2의 diversity-aware coreset은 expert 5개 중 4개에서 아무 일도 하지 않는다.**
exp28은 그 경우 refit을 건너뛰고 `2f_bank_block_sizes.csv`의 `identical_to_residual`·
`selector_active` 열에 기록한다.

**삭제**: `exp_groupcal`(q_corr를 expert별로) — 원인 C에서 출력이 class-상수임이 확인돼
grouping으로 복원 불가. min-support fallback도 verifier 수리 **이후로** 미룸(SSH expert를
살려도 brute의 g_lower 상한이 −18.43이라 채택 0).

### 2.3 exp26 — 사후 휴리스틱이 아니려면 무엇을 고쳐야 하는가

**먼저 지적을 받아들인다.** "`G > 0`으로 바꾸자"는 제안은 g_lower 표를 **보고 나서** 나왔다.
그대로 두면 "infiltration이 막혀 있으니 막은 규칙을 바꾼다"는 결과 주도 선택이고, §2.1에서
스스로 금지한 것과 같은 종류다. 그래서 knob을 다시 정의한다.

**정당한 것과 아닌 것의 경계**
- **정당**: *단위 오류*를 고치는 것. 현재 규칙 `q̂ > 21.145`는 클래스마다 w_c가 0.164~1132.8로
  **4자릿수 다른 양**에 **하나의 절대 문턱**을 적용한다. 이건 결과와 무관하게 그 자체로 틀렸다.
  차원이 다른 값을 같은 자로 재고 있다.
- **부당**: 문턱값이나 목표를 *어느 클래스가 열리는지 보고* 고르는 것. `G > 0`의 `0`에는
  아무 근거가 없다 — G = +0.001인 행도 자격을 얻는다. 그리고 부호만 쓰면 가이드 §14의
  보수적 하한(안전 장치)이 통째로 사라진다.

**따라서 exp26의 one knob을 "목표의 단위"로 바꾼다** (결정이론은 그대로):

```
현재    target  G_ik = L_i0 − L_ik            # w_bal 가중 CE, 스케일 6자릿수
        model   XGBRegressor(reg:quantileerror, α=0.25) → q̂
        accept  q̂ − q_corr > τ_post,  q_corr = 21.145 (스칼라)

exp26   target  G_ik / w_bal(y_i)             # ΔNLL 단위 — w_c가 나눠져 사라짐
        model   동일 (quantile α=0.25)
        calib   동일 절차 (D_cal에서 one-sided correction)
        accept  동일 (하한 > τ_post),  τ_post는 기존 제약 그리드로 선택
```

- **B가 풀리는 이유(구성상)**: 문턱이 더 이상 w_c에 비례하지 않는다. 클래스 필터가
  **정의에 의해** 사라지므로, 어느 클래스가 열리는지를 보고 고른 게 아니다.
- **C도 같이 완화된다**: 목표 스케일이 6자릿수 → 2자릿수로 압축되어 pinball loss가 스케일이
  아니라 판별에 맞춰진다. r ≈ 0.1이 개선되는지가 직접 검증 대상이다.
- **안전 장치 보존**: 하한·보정·제약 그리드가 그대로다. 가이드 §14의 구조를 유지한다.

**exp26b(별도 run) = 부호 분류** 는 *추정기 비교*로 강등한다. 같은 결정
(`P(G>0) > τ`)에 대한 다른 추정기이고, scorer에서 이미 검증된 처방이라는 근거는 있지만
단위 수정만큼 원리적이지는 않다. exp26이 부족할 때만 돈다.

**사후 선택이 아님을 증명하는 방법 — run 전에 아래를 등록한다.** 단위 수정이 맞다면
**모든** 클래스에 대해 방향이 예측 가능해야 하고, 하나라도 어긋나면 가설이 틀린 것이다.

| 클래스 | run 전 예측 | 어긋나면 |
|---|---|---|
| ddos | 자격 0% → 자격 발생, 채택 > 0 | 단위가 원인이 아니었음 |
| infiltration | 채택 0 → > 0 | 원인 C가 단위가 아니라 feature 문제 |
| **benign** | **여전히 거의 채택 안 됨** | 문턱만 낮춘 것 = 실패 |
| dos | 이미 91% 소진 → 큰 변화 없음 | 기존 dos 이득이 우연이었음 |
| brute | 여전히 0 (expert 부재) | 다른 설명 필요 |
| harmful | ≤ 200, benign FPR 증분 ≤ 0.0005 | 안전 장치 무효 |

특히 **benign은 열리면 안 된다**는 조건이 이 실험을 반증 가능하게 만든다. 부호 분류(exp26b)는
benign 제안 523,476행을 함께 열 위험이 크고, 그래서 exp26 다음이다.

### 2.4 exp27의 성격 — split 변경이 맞고, 트레이드오프가 있다

현재 pool 분할(context 50% / expert 25% / route 25%)이 **클래스 내부 시간순**이라 C0의 brute는
전부 FTP다(§1 원인 A). C0 안에서 아무리 잘 뽑아도 SSH는 D_expert·D_route에만 있으므로,
**추출 방식이 아니라 분할 자체를 바꿔야 한다**: 같은 50/25/25를 유지하되 **scenario 층화**로.
held-out 성질(D_expert가 C0에 없음)은 그대로 보존된다.

대가: "context가 test보다 시간상 앞선다"는 성질을 잃는다. 두 갈래 중 선택해야 한다.
- **(i) 공정 IID 우선** — 가이드 §21이 "XGB를 PFN context 크기로 제한하지 말라"고 한 것의 대칭:
  XGB가 pool 전체를 보는 만큼 C0도 pool 전체를 대표해야 한다. **E-0.5가 이 선택의 근거를 준다.**
- **(ii) 시간 서사 우선** — 현 chrono 분할을 "늦게 등장한 공격은 context에 없다"는 배포 조건으로
  두고 refresh(E-9)로 푼다. 단 이 경우 IID 표에서 XGB와의 brute 격차를 **method 열세로 보고하면
  안 된다**(정보예산 차이).
지금은 (i)로 진행하고 (ii)는 E-8의 전역 재분할에서 별도 축으로 다룬다.

### 2.3 중단·전환

## 3. 클래스별 성능 외의 평가지표

**전제 — metric shopping이 아닌 이유.** 가이드 §20.2가 **지기 전에** "RACE가 모든 IID setting에서
XGBoost를 이길 필요는 없다, 다만 general 성능과 benign safety를 훼손하면 안 된다"고 선언해 뒀다.
조건 셋: ① IID 표를 **지는 숫자까지 그대로** 1번 표로 유지, ② XGB를 **같은 run**에서 계산,
③ 각 축의 문턱을 run 전에 등록.

### 축 A (1차) — 조건부 개입의 안전성과 운용점

주장: *"frozen FM 위에 되돌릴 수 없는 손해 없이 조건부 교정층을 얹고, 운용점을 보정으로 통제한다."*

- 지표: 클래스별 4-way transition(§22) + harmful rate + Clopper–Pearson CI, override precision,
  benign FPR 증분, net correction/1M, ECE.
- 현재: helpful 12,710 / harmful 4 → precision 0.9997, benign FPR 0.004139 vs 0.004138(불변),
  ECE 0.0079 vs 0.0091, balanced acc 0.6941 vs 0.6647.
- **대조군이 결정적**: 같은 bank에서 verifier만 빼면 `top1_noverify` 0.5199,
  `nearest_centroid` 0.4572 — **검증 없는 라우팅은 −0.18~−0.24로 붕괴**한다.
  XGB가 아니라 라우팅/MoE 문헌과 겨루는 명제.
- **harm–gain 프론티어**(핵심 그림): exp22c 0.7428/harmful 8,524/1.60회 ↔ 24b-off
  0.6978/harmful 4/1.16회. 같은 시스템의 운용점 선택 문제로 제시.
- 정직성 가드: "채택 행에서 global 0.0012 → 시스템 0.9991"은 gain으로 선택된 부분집합이므로
  **단독 인용 금지**, (채택 수, 비율, harmful CI) 3종 세트로만.
  harmful 4는 τ 그리드 전 구간에서 0~1이므로 **판별력이 아니라 운용점의 성질**임을 명시.

### 축 B (1차) — context 갱신/보강

원래 "authentic temporal drift 회복"으로 세우려 했으나 **원인 A가 근거를 무너뜨렸다**(사건이
train pool 안에 있고 XGB가 recall 0.9998로, 무작위 블록도 푼다). 살아남는 형태 둘:

1. **context coverage**(즉시): "1M context를 클래스내 시간순이 아니라 scenario-피복으로 뽑으면
   무엇이 회복되는가". 가이드 §6이 이미 요구하던 것. 대조: chrono C0 / random C0 / stratified C0.
2. **§17 prequential refresh**(전역 재분할 후): 같은 공개 행으로 4 arm —
   (i) B=0, (ii) XGB warm-start, (iii) XGB 전체 재학습, (iv) **experts·scorer·verifier 없이
   B행을 C0에 붙인 global**. (iv)가 가장 싸고 가장 치명적인 대조군.
- 지표: window별 macro/tail, **라벨당 회복량**, 적응 wall-clock, forgetting.

### 보조 축 (표는 만들되 단독 주장 금지)

- **선택적 예측**: `g_lower` 기반 risk–coverage + AURC. 오늘 offline 확인 — 시스템이 모든
  coverage에서 global 우위(cov 1.0 err 0.0374 vs 0.0405). **y축은 balanced/cost-weighted risk**
  (macro-F1은 coverage에 비단조 — cov 0.95에서 0.649로 하락).
- **비용(§20.6)**: 호출률·wasted call·latency p50/p95/p99·peak GPU. 실측 배수 **2.044×**로 적고,
  "XGB보다 싸다"는 주장은 하지 않는다(비교 대상은 dense all-expert).
- **regime 단위 평가**: 활성률 15.76%의 개입이 클래스 평균에서 희석되는 것을 드러내는 진단용.
- **unique-hash view**: 중복 48%를 제외한 재계산을 oracle·per-class 표에 병기(원인 E-3).

### 축별 baseline 공정성 (어기면 전부 무효)

| 축 | 요건 |
|---|---|
| A | XGB는 개입 대상이 아님 → 비교는 다른 라우팅 정책(no-verify, nearest-centroid, dense oracle). 매칭된 채택 수의 random-null 필수 |
| B | 같은 B행으로 XGB warm-start·전체 재학습 **둘 다**, 같은 wall-clock에서 |
| 선택적 예측 | XGB에 D_cal temperature scaling + 동일 confidence 정의 |
| 비용 | global PFN 자신의 비용 포함, 호출 수를 wall-clock 배수로 환산 금지 |
| 전 축 | `8a`가 보여주듯 known-prior 보정을 주면 XGB가 압승 — 그 표를 숨기지 않는다 |

### 항상 같이 보고할 표

① IID guardrail(per-class + macro/tail/balanced acc/AUPRC/benign FPR/ECE, XGB 3종·global·oracle
동일 run) ② intervention(transition+CI, 프론티어, no-verify 대조) ③ cost ④ selective
⑤ temporal ⑥ 재현성(최종 구성만 5 seed + scenario/day paired block bootstrap, 모든 표에 E-2 대역 병기)
