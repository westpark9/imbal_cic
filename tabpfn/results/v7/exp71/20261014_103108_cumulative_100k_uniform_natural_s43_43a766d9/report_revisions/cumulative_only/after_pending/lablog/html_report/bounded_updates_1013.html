1. 새 공격을 어떤 순서와 구성으로 추가했는가

초기에는 Benign과 두 공격 클래스로 시작한다. 다음 단계마다 새 공격의 라벨 사례와 Benign 사례를 함께 공급하고, 그때까지 도입된 클래스의 고정 test 행에서 두 모델을 평가한다. 새 클래스의 라벨 사례는 해당 클래스의 평가 전에 제공한다.

초기 구간과 일부 인접 클래스를 묶되 최초 출현의 상대적 순서를 유지했다. 원본 timestamp에 따른 트래픽 재생이나 미관측 공격의 라벨 없는 탐지를 평가한 것은 아니다.

공격 내 자연 비율은 전체 트래픽의 자연 분포를 뜻하지 않는다. 두 모델은 같은 조건에서 동일한 학습·test IDs를 사용한다. 균등/자연 배정은 최종 총량과 Benign IDs를 맞추며, 공격별 사례 수와 중간 단계의 입력 크기는 달라진다.

클래스별 공급량·test 표본 수와 최초 출현일

표는 해당 데이터셋의 전체 test 표본 수 내림차순. 공급량은 실험 전체에 제공한 서로 다른 행 수이며 최종 누적 context에 모두 포함된다. 최초 출현일은 원본 기록의 UTC 기준이다.

2. 갱신이 빠른가, 추론까지 효율적인가

갱신은 새 라벨 사례를 반영해 다음 예측을 준비하는 비용이고, 추론은 준비된 모델로 test 행을 예측하는 비용이다. TabPFN이 가중치를 재학습하지 않는다는 사실이 두 비용 모두 낮다는 뜻은 아니다.

누적 전체에서 갱신이 느려질 수 있는 이유: 현재 구현은 매 단계 누적 전체 context로 fit_with_cache를 다시 호출한다. TabPFN은 가중치를 학습하지 않지만, ensemble 4개의 전처리·context 인코딩·캐시를 다시 구성한다. 이는 새 사례만 캐시에 추가하는 방식이 아니며, 입력이 커질수록 갱신 비용도 늘 수 있다. XGB도 같은 전체 사례로 300개 트리를 새로 학습한다. 구간별 실측 시간은 아래 토글에서 확인할 수 있다.

4. 이 결과가 TabPFN을 채택할 근거가 되는가

입력 규모를 늘려 필요한 탐지 품질을 확보할 수 있는지 확인

현재 후속 실험은 최종 누적 입력을 두 데이터 모두 10만 행으로 확대하는 것이다. Benign 7.5만·공격 2.5만을 공급하며 공격 균등과 공격 내 자연비율을 비교한다. 과거 사례는 모두 유지하고 클래스 출현 순서·평가 test·모델 설정을 고정한다. 성능 개선 여부와 함께 갱신·추론 비용 증가를 확인한다.

규모를 확대해도 자연비율 조건의 소수 공격 사례 수는 여전히 적을 수 있다. 균등 조건과 함께 보면 전체 입력량뿐 아니라 공격별 확보 라벨 수에 따른 차이를 확인할 수 있다. 단일 seed 비교이므로 분포 효과나 개별 클래스의 실패 원인을 확정하는 인과 실험으로 해석하지 않는다.

이 결과는 단일 TabPFN·XGBoost 비교다. 제안 모델의 expert·S/V 기여와 구별하며, 가중치 재학습이 없다는 사실만으로 갱신 시간이나 운영 총비용의 우위를 주장하지 않는다.
